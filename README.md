# BYTE BACK 나의 자료실 · 12단계 작업 저장점

현재 기반은 11단계 저장점 복원 커밋 `910019f`이며 이번 저장점의 설정 단계는 12입니다. 단계 번호는 작업 진행 표시이며 통과 결과가 아닙니다. 12단계 준비 작업으로 `/ops.html`과 `/api/ops`를 추가했습니다. 공식 운영 결과 조회 연결이 없어 API는 현재 503을 반환하고 화면은 원본 미연결로 표시합니다. 실제 결과 연결·12단계 완료·41종 방어 완료를 뜻하지 않습니다. 구현 범위와 확인 명령은 [작전실 원본 연결 안내](docs/OPERATIONS_SOURCE.md)에 정리했습니다.

이 저장소는 시작 틀 R5에서 출발해 1~11단계 기능을 추가한 실습용 자료실입니다. 기존 메모는 가상 자료이며 실제 학생 자료, 토큰, 비밀키를 넣지 않습니다.

## 설치·실행·확인

1. Node.js 22 이상과 Git을 준비합니다. 기존 작업 폴더를 보존하고 **새 폴더**에서 검사 기준 코드를 받습니다. 다음 명령의 체크아웃은 새로 받은 폴더에서만 실행합니다.

   ```powershell
   git clone https://github.com/darong9494/choi-bujang-secret-vault.git choi-bujang-checked
   cd choi-bujang-checked
   git checkout --detach 3e8802976a0c0087319e4f740e0fdab808bdb70f
   npm install
   ```

2. 학생 판정기는 `npm run decider:test`, 탐지 규칙은 `npm run detect:test`로 실행합니다. 판정기의 정상 등록 기기 요청은 `allow`, 미등록 요청은 `deny`여야 합니다. 탐지는 정상 사건에서 `observe`, 조회 폭주에서 `propose_revocation`이어야 합니다. 모두 로컬 가상 연습이며 운영 엔진·심판 결과가 아닙니다.
3. 작전실·실측 표의 로컬 검증은 `node --test test/request-checks.test.mjs test/operations.test.mjs`입니다. 검사 기준 코드에서 18개가 통과했습니다. 화면용 계약·가림·미실행 구분을 확인하는 시험이며 실제 보호자료 허용·접속 회수·복구를 증명하지 않습니다.
4. 접속 앱·자료실은 Vercel에서 해당 커밋을 배포해 실행합니다. 화면은 `public/`, 서버 함수는 `api/`, 빌드 명령은 `npm run build`입니다. Vercel의 Git 정보와 배포 URL이 필요합니다. 로컬 정적 생성만 확인할 때는 `npm run build -- --local`이며 API 서버를 실행하는 명령은 아닙니다. 이 저장소에는 `npm start` 스크립트가 없습니다.
5. 배포 후 `/aleph.json`의 커밋을 검사 기준 SHA와 대조합니다. [자료실](https://choi-bujang-secret-vault-beta.vercel.app/)에서 로그인·기기 상태를 확인하고 브라우저 메뉴의 앱 설치 또는 홈 화면에 추가를 누릅니다. 정상 확인은 설치 안내와 기기 상태가 나타나는 것입니다. 현재는 기기 승인 원본이 없어 로그인 후에도 보호 메모가 열리지 않아야 합니다.
6. 자료실의 **현재 로그인 상태로 실측 기록 만들기 → 실측 기록 JSON 저장**을 누릅니다. 비로그인 확인은 `/checks.html`의 **로그인 없는 요청 실측**을 사용합니다. 정상 공개 화면은 HTTP 200, 비로그인·위조 신원의 보호자료 요청은 HTTP 401이어야 합니다. 정상 보호자료 허용은 실제 서버 승인과 HTTP 200을 확인할 때만 기록합니다. 절차와 각 행의 뜻은 [실측 안내](docs/REQUEST_MEASUREMENTS.md)에 있습니다.
7. `/ops.html`에서 **운영 결과 다시 조회**를 누릅니다. 현재 정상 동작은 HTTP 503·원본 미연결·수치 미표시입니다. 가린 서버 기록과 화면 수치는 같은 응답으로 대조하며 원본이 없으면 성공 수치를 만들지 않습니다. 실제 심판 판정은 제출 포털에서 확인합니다.

현재 확인 범위: 익명 실측에서는 금지 요청 5건의 HTTP 401과 실제 응답 요청 ID·확인 시각을 확인했습니다. 정상 보호자료 허용은 미실행이며 복구 경로의 404는 거부 성공으로 세지 않습니다. 41종 총공세도 미실행입니다. 다시 실행하면 그때 받은 응답·요청 ID·시각으로 새 기록을 남깁니다.

`/`에서는 로그인과 서버의 기기 승인 확인을 모두 통과해야 메모를 요청하고 표시합니다. 현재 기기 상태 API는 운영 엔진의 등록 정보가 연결되지 않아 로그인 후에도 `approved: false`를 반환하므로 화면에서 메모가 열리지 않습니다. 자료 API 자체는 로그인·소유자를 검사해 Supabase의 메모를 처리하지만 판정기를 직접 호출하지는 않습니다. `/data.json`은 빈 목록만 제공하며 메모를 담지 않습니다.

Vercel 프로젝트 설정의 Environment Variables에 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` 또는 `SUPABASE_ANON_KEY`, 서버 전용 `SUPABASE_SECRET_KEY`를 직접 입력하고 재배포합니다. 값은 코드·Git·로그·답변에 넣지 않습니다. Supabase `notes` 테이블의 기존 가상 메모와 소유자 자료는 보존합니다.

## 중지·복구와 제출 범위

- **로컬 중지:** 판정기·탐지·검증·빌드는 한 번 실행 후 종료합니다. 실행 중 중단은 터미널에서 `Ctrl+C`입니다. 접속 앱은 로그아웃 후 창을 닫습니다. 앱 종료·삭제만으로 엔진 접속 회수가 완료된 것으로 기록하지 않습니다.
- **서비스 중지:** 접속 앱 창을 닫아도 Vercel API는 계속 동작합니다. 서비스 자체를 중지해야 하면 Vercel의 서비스 제공을 중지하고, 제공 엔진의 접속 회수는 운영 담당자가 별도로 확인합니다. 중지 과정에서 학습 DB·기존 감사 이력·다른 작업을 삭제하지 않습니다.
- **학생 코드 복구:** 위의 새 폴더 재현 순서로 검사 기준 커밋을 받거나 그 커밋의 Vercel 배포를 다시 배포합니다. 기존 작업 폴더를 강제로 초기화하지 않습니다. 공식 설정 화면의 환경변수 설정을 유지하고 `/aleph.json` 커밋 대조 → 로컬 가상 연습 → 실제 읽기 실측 순으로 재확인합니다. 복구 뒤 정상 공개 화면 200·금지 요청 401을 확인하고, 보호자료 허용은 실제 승인 없이는 미실행으로 남깁니다.
- **엔진·자료 복구:** 코드 재배포는 메모·정책 복구가 아닙니다. 제공 엔진의 검증된 백업과 정책 버전이 필요하며 아래 10단계 순서로 지정한 한 건만 복구하고 감사 기록을 확인합니다. 현재 복구 API는 구현되지 않았으므로 실제 복구는 미실행입니다.
- **비밀값 제외:** 설치·복구 시 필요한 값은 공식 비밀 설정 화면에 직접 입력합니다. `.env*`, 비밀번호·토큰·기기 개인키·서버 전용 키·실제 개인정보·메모 본문을 ZIP에 담지 않습니다. 엔진 비밀 설정과 DB 백업도 포장하지 않습니다. `bundle-notes.json`과 `artifacts/submission.json`은 Git에서 제외하며, 무시 파일도 수동 ZIP에는 들어갈 수 있으므로 별도로 제외합니다. 이 문서 수정에서는 제출 묶음을 생성하지 않았습니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`은 이 프로젝트의 GitHub 저장소 주소이고, `publicAppUrl`은 현재 공개 자료실 주소(`https://choi-bujang-secret-vault-beta.vercel.app/`)입니다. 이 값들은 배포·로그인 검증·제출 묶음에서 사용하므로 실제 프로젝트 주소와 일치해야 합니다. 현재 설정 단계는 12이며 운영 원본 미연결 상태의 작전실을 12단계 완료로 보고하지 않습니다.

로컬에서 배포 식별정보 없이 정적 결과물만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 이 빌드는 `public/data.json`에 빈 목록을 생성합니다.

## 다음 단계의 코딩 도구에 전달할 규칙

[AGENTS.md](AGENTS.md)를 먼저 읽히고 한 번에 한 제작 단위만 요청하세요. 2단계부터는 자료 보호를 구현할 때 `public/data.json`을 복사하는 1단계 빌드 흐름도 함께 바꿔야 합니다. 3단계 이후의 로그인, 허용 경로, 5단계의 원본 API 주소, 6단계 이후 정책 규칙은 해당 단계 원고와 계약에 맞춰 추가합니다. 비밀번호·토큰·서버 전용 키·실제 학생 기록을 코드, Git, 제출 묶음에 넣지 않습니다.

`src/decider.mjs`와 `src/detect.mjs`의 로컬 시험은 반 엔진이나 운영 심판의 결과가 아닙니다. 1단계 이후 제출 묶음 계약 `aleph.defense.submission.v2`는 `scripts/bundle.mjs`에 남아 있으며, 코딩 도구가 해당 단계의 최신 배포 주소와 Git 원격을 맞춘 뒤 사용합니다.


## 6단계: 등록한 기기만 자료실에 들어옵니다

`src/decider.mjs`의 `decide(request)`는 `docs/DECIDER_REQUEST.md`에 있는 요청 이름을 사용합니다. 현재 구현은 확인된 식별정보·기기 등록 여부·경로에 더해 7단계에서 추가한 `signals`, `recentEvents`, `stepUp`도 검사합니다. 등록 여부가 `true`가 아니거나 식별정보·기기 ID가 유효하지 않으면 `deny · device_not_registered`입니다. 기기 규칙은 `device_registered`이며, 전체 `RULE_IDS`는 `device_registered`, `resource_scope_access`, `step_up_required` 세 개입니다. 현재 허용 경로는 아래 8단계에 정리했습니다.

### 6단계 판정기 확인 순서

1. 저장소 루트에서 `npm run decider:test`를 실행합니다.
2. 등록된 기기의 정상 요청에서 `통과 · 등록 기기의 정상 요청 · allow · approved`가 나오는지 확인합니다.
3. 미등록 기기의 가상 요청에서 `통과 · 미등록 기기의 가상 요청 · deny · device_not_registered`가 나오는지 확인합니다.

별도 접속 프로그램 설치는 필요하지 않습니다. 이 명령은 가상 요청을 사용하는 로컬 연습이며, 운영 엔진 연결이나 심판 판정을 증명하지 않습니다. 미등록 기기 공격 판정은 심판이 맡습니다.

현재 `/api/notes`는 로그인 확인 후 로그인 사용자 소유의 메모를 읽고 씁니다. 하지만 이 API는 `decide()`를 호출하지 않으며, 엔진이 확인한 `deviceRegistered` 요청을 전달받는 연결도 없습니다. 따라서 6단계 판정기 규칙은 로컬 판정 요청에 구현되어 있지만 실제 `/api/notes` 접근에는 아직 적용되지 않습니다. 기존 자료실 주소와 브라우저 화면은 그대로입니다.

## 7단계: 복합 이상 접속은 다시 확인합니다

`step_up_required` 규칙은 엔진 요청의 최근 `risk_signal` 사건(300초 이내·횟수 10 이상), 비정상 네트워크, 이른/늦은 시각(0~5시 또는 23시)이 함께 있을 때 `step_up`을 요청합니다. 지역 값만으로는 거부하거나 추가 확인을 요구하지 않습니다. 요청의 `stepUp.verified`가 참이고 엔진이 확인한 `authAgeSeconds`가 0~900초일 때만 이 가상 조합을 통과시킵니다.

로컬 가상 연습은 `npm run decider:test`입니다. 정상 조합은 `allow`, 복합 이상 조합은 `step_up · step_up_required`, 엔진 검증 재로그인 시각이 있는 가상 요청은 `allow`여야 합니다. 브라우저 위치는 사용하지 않으며, 실제 재로그인 검증은 제공 엔진이 확인한 시각이 전달될 때만 시험할 수 있습니다. 이 연습은 운영 엔진 접속이나 심판 판정이 아닙니다.

현재 제공 계약은 `stepUp.verified`와 `authAgeSeconds` 필드만 정의하며, 같은 로그인 사용자의 새 로그인 확인을 자료 API까지 강제하는 연결은 확인되지 않았습니다. `/api/notes`와 `/api/notes/:id`는 `decide()`를 호출하지 않으므로 추가 확인 전 자료 차단 및 새 로그인 뒤 허용은 미실행입니다. 실제 엔진 연동 전에는 로컬 가상 사건만 확인합니다.

## 8단계: 자료마다 갈 수 있는 구역을 나눕니다

`resource_scope_access`는 엔진이 확인한 주체·등록 기기 조건을 통과한 `notes` 서비스 요청 중 개별 메모의 `GET`·`PUT /api/notes/:id`만 경로 조건으로 허용합니다. `/notes/:id` 별칭도 지원하며 `route`가 메서드·경로 모양과 일치해야 합니다. ID는 비어 있거나 `.`·`..`이면 안 되고 `/`·`?`·`#`를 포함할 수 없지만, 판정기 자체는 UUID 형식을 검사하지 않습니다. 목록·생성·삭제 요청과 다른 서비스·경로는 `deny · starter_not_ready`입니다. 경로 조건을 통과해도 위험 입력·추가 확인 조건에 따라 거부되거나 `step_up`이 될 수 있습니다.

현재 자료 API는 로그인한 Supabase 사용자 ID로 목록을 소유자 필터링하고, 개별 메모의 조회·수정·삭제에서도 소유자를 확인합니다. 하지만 `/api/notes`와 `/api/notes/:id`는 `decide()`를 호출하지 않으므로 `resource_scope_access` 판정이 실제 API 권한 검사로 전달되지는 않습니다. 판정 요청 계약과 자료 스키마에는 강사 역할이나 공지 구역도 없어서 이를 임의로 허용하지 않습니다.

로컬 판정기 연습은 저장소 루트에서 `npm run decider:test`로 실행합니다. 이는 가상 요청 확인이며, 기존 fixture는 등록 기기 노트 읽기, 미등록 기기 거부, 복합 이상 접속의 추가 확인을 확인합니다. 실제 API의 역할별 구역 분리나 판정기 연동을 증명하지 않습니다.

## 9단계: 도플갱어를 찾고 권한 회수를 제안합니다

`src/detect.mjs`는 같은 가명 주체와 같은 유효 기기의 `GET` 조회가 10분 미만 창에서 120건을 초과하면 별도 결과로 `propose_revocation`과 `burst_read`를 반환합니다. 기기 ID가 주어지면 그 한 기기를 대상으로 반환합니다. 제작자 통과 표본의 최소 사건 형식에는 기기 ID가 없어 가명 주체를 반환합니다. 실제 권한 회수와 탐지부터 회수까지의 시간 측정은 미실행입니다.

로컬 가상 사건 확인은 저장소 루트에서 `npm run detect:test`로 실행합니다. 같은 주체·기기의 10분 미만 조회가 120건을 초과하면 `propose_revocation · burst_read`, 그 밖에는 `observe`입니다. 비정상 네트워크·지역 등 추가 신호는 필수 조건이 아닙니다. 유효한 기기 ID가 있으면 `target.deviceId`, 없으면 가명 `subject`를 반환합니다. 실제 반 엔진 전달이나 심판 판정은 이 시험으로 확인되지 않습니다.

## 10단계: 백업에서 자료실을 되살립니다

`aleph.config.json`의 `restoreRoute`는 `/api/restore/:noteId`입니다. [제작자 공식 통과 표본](https://github.com/ChoiTimo/byteback-sample-pass)의 역할 구분에 따라 백업 보관·검증, 실제 복원 집행, 감사 기록 보관은 제공 엔진이 맡습니다. 학생 저장소에는 엔진의 백업 원본과 감사 저장소가 없습니다. Vercel 서버 함수가 현재 메모를 임의의 사본으로 간주해 복원하거나 감사 성공을 선언하지 않습니다. 9단계 통과 커밋 `657381cbfdd74d17dffc5d0a2a38f314278e8ff5`의 `src/decider.mjs`, `src/detect.mjs`, `allowedRoutes`는 변경하지 않았습니다.

### 1. 백업 검증과 실행 전 차이 확인

1. 엔진이 보관한 침해 전 안전 정책 사본을 **다시 읽고** 무결성을 확인합니다. 사본이 없거나 읽기·검증에 실패하면 복원하지 않고 검증 실패로 기록합니다.
2. 사본의 `policyRevision`을 복원 대상으로 지정한 정책 버전과 대조합니다. 다르면 중단합니다.
3. 복원 실행 전에 현재 정책과 사본의 버전 및 변경 항목을 보여 줍니다. 변경 범위가 지정한 가상 메모 **한 건** 밖의 메모 또는 다른 서비스 규칙까지 포함되면 중단합니다. 이 저장소에 있는 오래된 로컬 파일로 엔진 정책을 덮어쓰지 않습니다.

### 2. 지정한 가상 메모 한 건 복원

1. 검증된 사본에서 ID와 소유자를 확인한 한 건만 `/api/restore/<noteId>`에 지정합니다. 다른 가상 메모와 1~9단계의 정상·거부 규칙은 그대로 둡니다.
2. 복원 뒤 해당 한 건을 다시 읽어 ID·소유자·내용의 SHA-256을 사본과 비교합니다. 하나라도 다르면 실패로 기록하고 성공으로 처리하지 않습니다.
3. 기존 감사 이력은 삭제하거나 수정하지 않습니다. 검증 실패와 복원 결과를 보존하고, 복원 작업 자체를 감사 기록에 새 항목으로 남깁니다. 엔진 감사 기록을 확인하기 전에는 감사 보존을 완료했다고 보고하지 않습니다.

### 3. 복원 뒤 재시험

복원 뒤 확인할 항목은 비로그인·위조 신원 거부, 등록·미등록 기기 판정, 자기 메모 허용과 타인 메모 거부, 허용 경로 제한, 복합 이상 재확인, 조회 폭주 탐지, 지정한 메모·감사 이력 보존입니다. 이는 재시험 절차이며 실제 엔진 복원 완료 기록이 아닙니다. `npm run decider:test`, `npm run detect:test`는 가상 요청 연습입니다. 현재 `npm run bundle`의 자기 점검은 실제 HTTP 요청에 `alephEvidence: { caseId: attackId, requestKey: "read" }`를 연결하고 응답 상태만 기록합니다. 이 값은 요청 헤더·URL로 전송하지 않는 실행 관측 메타데이터입니다. HTTP 요청 없이 로컬에서만 연습하는 판정·탐지 항목은 제출 기록의 `observed`를 정확히 `not_run`으로 남깁니다. 복구 경로의 404는 권한 차단 성공으로 세지 않습니다. 실제 인증 사용자·엔진 복원·감사를 확인하지 못한 항목은 미실행입니다.

## 11단계: 나만의 접속 앱을 완성합니다

`public/manifest.json`은 앱 이름 「나의 자료실」, 시작 화면, 독립 실행 표시와 아이콘을 정의합니다. HTTPS 배포 화면에서 브라우저의 앱 설치 또는 홈 화면에 추가를 사용할 수 있습니다. 별도 설치 프로그램은 없으며, 오프라인에서는 로그인·기기 승인 확인과 메모 읽기가 불가능하다는 안내를 화면에 표시합니다. 보호 메모와 기기 키는 브라우저 오프라인 저장소에 보관하지 않습니다. 로그인 세션도 페이지 메모리에서만 사용하므로 새로 열면 다시 로그인해야 합니다.

로그인하면 화면이 서버의 `GET /api/device/status`를 확인합니다. 승인 전에는 메모 목록 조회를 보내지 않고 메모 목록·편집 폼을 숨깁니다. 설치 완료, 버튼 클릭, 브라우저 저장소 값은 승인 근거가 아닙니다. 서버는 신원을 확인한 뒤 현재 운영 엔진의 기기 등록 정보를 받을 계약이 없으므로 `approved: false`를 반환합니다. 이 연결 전에는 실제 승인된 기기의 자료실 개방을 완료했다고 말할 수 없습니다. 승인 사실은 엔진이 확인한 기기 등록 상태가 서버에 안전하게 전달될 때만 응답해야 합니다. 기존 `/api/notes`는 로그인·소유자 검사와 이전 단계 기능을 유지합니다.

확인: 배포 주소를 열고 브라우저 메뉴의 앱 설치 또는 홈 화면에 추가를 누릅니다. 정상 확인은 설치 안내와 서버 기기 상태가 표시되는 것입니다. 거부 확인은 비로그인 `GET /api/device/status`가 HTTP 401이고, 로그인만 했거나 앱만 설치한 상태에서 메모가 나타나지 않는 것입니다. 엔진이 승인한 기기의 실제 메모 열람은 엔진 연동 전까지 미실행입니다. `npm run bundle`은 앱 실행 명령이 아니라 제출 묶음 생성 명령이며, 커밋된 깨끗한 작업 폴더와 별도 `bundle-notes.json`이 필요합니다. 두 제출용 파일 `bundle-notes.json`, `artifacts/submission.json`은 Git에 넣지 않습니다.

## 보너스 XDR: 무차별 로그인 공격 연습

`xdr/brute-force/patterns.json`은 MITRE ATT&CK T1110 근거가 있는 두 연습 패턴을 담고, `xdr/brute-force/decide.mjs`는 가상 경보를 `block`·`alert`·`record`로 분류합니다. 저장소 루트에서 `npm run xdr:run -- brute-force`를 실행하면 결과를 `xdr/brute-force/result.json`에 갱신합니다. 결과는 fixture를 사용한 로컬 자기 점검이며 실제 ZTNA 차단이나 심판 판정이 아닙니다.

## 보너스 xdr-03 저장점: 알려진 취약점 악용 검사

`xdr/known-cve/decide.mjs`는 패턴 상수를 가진 단독 판정 모듈입니다. CVE-2021-44228·MITRE T1190 근거와 모호한 보조 신호를 구분하고, 완전한 악용 형태만 block, 모호한 흔적은 alert, 일반 이벤트는 record로 분류합니다. 별도 읽기 모듈은 지정한 다섯 항목만 추출하고 비밀값 의심 필드를 가립니다.

다시 실행: `npm run xdr:run -- known-cve`. 가상 경보 24건의 `result.json` 집계는 block 8·alert 8·record 8이며 정상 이벤트 차단은 0건입니다. 관련 로컬 시험 13개가 통과했습니다. 별도 화면 버튼은 없습니다.

`node xdr/known-cve/respond.mjs --fixture`는 명확한 공격 요청 지문에만 기본 10분 만료·근거 경보 번호가 있는 추가 거부 규칙을 저장하고 알림을 `xdr/alerts.log`에 한 줄씩 남깁니다. 규칙·로그는 Git에서 제외합니다. `check-access.mjs`가 기존 ZTNA 규칙을 보존하며 추가 검사를 결합합니다. 운영 ALEPH SDP 엔진의 경보 전달·집행과 공용 저장소는 미연결입니다. 단계는 12를 유지하며 로컬 결과를 운영 차단·심판 통과로 보고하지 않습니다. 자세한 범위와 재현 방법은 [모듈 안내](xdr/known-cve/README.md)에 있습니다.
